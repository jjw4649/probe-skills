# 블랙박스 시험과 데모 동선

## 언제
기능 동결 직후, 구현하던 대화가 아닌 **새 대화(/new)**에서 부른다. 만든 사람의 기억 없이 사용자 눈으로 보기 위해서다. /new 전에 HANDOFF.md를 지금 상태로 새로 써 둔다. 고칠 것이 나오면 새 대화에서 HANDOFF.md와 REVIEW.md를 읽고 이어 간다.

## 읽을 것
REQUIREMENTS.md, HANDOFF.md의 '실행 방법', 과제 README. **소스 코드는 읽지 않는다.** 화면에 무엇이 있는지는 curl 결과와 사람이 알려 준 결과로만 안다.

## 순서
0. 서버 확인: HANDOFF.md의 포트로 curl 한 번을 승인 요청한다. 응답이 없으면 "서버를 켜 주세요: (명령)"만 말하고 멈춘다. 서버는 사람이 켠다.
1. 시나리오를 만든다. 칸마다 하나씩.
   ① 정상 흐름: 핵심 흐름을 처음부터 끝까지
   ② 빈 입력: 아무것도 넣지 않고 실행
   ③ 잘못된 형식: 글자 자리에 숫자, 범위 밖 값, 이상한 파일
   ④ 경계값: 한계선 바로 아래와 바로 위
   ⑤ 권한: 다른 사람의 정보나 운영자 기능에 일반 사용자로 접근
   ⑥ 다시 열기: 새로고침, 서버 재시작 뒤에 결과·이력이 남는지
   ⑦ 동시 수정 (수정·확정 기능이 있을 때만): 브라우저 탭 두 개에서 같은 항목을 다르게 고쳐 차례로 저장. 기대: 뒤에 저장한 쪽에 경고가 보이거나 이력에 둘 다 남는다.
2. 시나리오마다: 관련 R | 내가 할 동작(3단계 이내) | 기대(성공 기준 문장) | 실제(빈칸, 사람이 채움).
3. R 대조표: REQUIREMENTS.md의 R마다 성공 기준(정상, 예외)을 하나씩 적고, 그 기준을 확인하는 시나리오 번호를 붙인다. 어떤 시나리오로도 확인되지 않는 기준이 있으면 시나리오 ⑧ 이후로 짧게 더한다(동작 3단계 이내). 결과 칸은 비워 둔다.
   표: R | 성공 기준 | 확인 시나리오 | 결과(빈칸)
4. curl로 확인할 수 있는 것은 승인 요청해서 먼저 돌려 보고 '실제' 칸에 "curl: ○○"로 적는다. 버튼을 눌러야 하는 것은 비워 둔다.
5. 데모 동선: 1순위 R이 가장 먼저 보이도록 클릭 5~7개, 3분 이내. 단계마다 "누르는 것 → 보이는 것 → 말할 한 줄(어떤 요구를 해결하는지)". 끝 단계는 예외 처리 하나를 보여 준다.
6. REQUIREMENTS.md의 '안 만드는 것'과 '미룸'이 화면에 반쯤 만들어진 채 보이지 않는지 한 줄 확인.
7. 모두 REVIEW.md의 '## 블랙박스 시험', '## R 대조', '## 데모 동선' 칸에 적는다(파일이 없으면 만든다).

## 멈추는 곳
REVIEW.md를 저장하고 이 넷만 보고한 뒤 멈춘다.
- curl로 이미 실패한 시나리오
- 사람이 직접 눌러야 하는 시나리오 번호
- R 대조에서 더한 시나리오 번호(없으면 "없음")
- 데모 동선 첫 세 단계

사람이 결과를 한 줄로 주면(예: "④ 실패: 46명도 통과됨, ⑤ 통과") '실제' 칸과 R 대조의 '결과' 칸을 그 말 그대로 채운다. 눌러 보지 않은 칸은 비워 둔다. 고칠 것은 사람이 1~2개 고르고, 고치는 일은 구현 대화에서 조각 하나로 한다.

## 하지 말 것
- 코드 읽기, 코드 고치기
- 눌러 보지 않은 시나리오나 확인하지 않은 기준을 통과로 쓰기
- 새 기능 제안
