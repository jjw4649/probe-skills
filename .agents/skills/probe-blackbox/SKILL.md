# 블랙박스 시험과 데모 동선

## 언제
기능 동결 직후, 구현하던 대화가 아닌 **새 대화(/new)**에서 부른다. 만든 사람의 기억 없이 사용자 눈으로 보기 위해서다. /new 전에 `$probe-close 인계`로 HANDOFF.md를 최신으로 만들어 둔다. 고칠 것이 나오면 새 대화에서 HANDOFF.md와 REVIEW.md를 읽고 이어 간다.

## 읽을 것
REQUIREMENTS.md, HANDOFF.md의 '실행 방법', 과제 README. **소스 코드는 읽지 않는다.** 화면에 무엇이 있는지는 curl 결과로만 안다.

## 순서
1. 시나리오 6개를 만든다. 칸마다 하나씩.
   ① 정상 흐름: 핵심 흐름을 처음부터 끝까지
   ② 빈 입력: 아무것도 넣지 않고 실행
   ③ 잘못된 형식: 글자 자리에 숫자, 범위 밖 값, 이상한 파일
   ④ 경계값: 한계선 바로 아래와 바로 위
   ⑤ 권한: 다른 사람의 정보나 운영자 기능에 일반 사용자로 접근
   ⑥ 다시 열기: 새로고침, 서버 재시작 뒤에 결과·이력이 남는지
2. 시나리오마다: 관련 R | 내가 할 동작(3단계 이내) | 기대(성공 기준 문장) | 실제(빈칸, 내가 채움).
3. curl로 확인할 수 있는 것은 승인 요청해서 먼저 돌려 보고 '실제' 칸에 "curl: ○○"로 적는다. 버튼을 눌러야 하는 것은 비워 둔다.
4. 데모 동선: 1순위 R이 가장 먼저 보이도록 클릭 5~7개, 3분 이내. 단계마다 "누르는 것 → 보이는 것 → 말할 한 줄(어떤 요구를 해결하는지)". 끝 단계는 예외 처리 하나를 보여 준다.
5. REQUIREMENTS.md의 '안 만드는 것'이 실제로 없는지 한 줄 확인.
6. 모두 REVIEW.md의 '## 블랙박스 시험'과 '## 데모 동선' 칸에 적는다(파일이 없으면 만든다).

## 멈추는 곳
REVIEW.md를 저장하고 이 셋만 보고한 뒤 멈춘다.
- curl로 이미 실패한 시나리오
- 내가 직접 눌러야 하는 시나리오 번호
- 데모 동선 첫 세 단계
'실제' 칸을 다 채우면 내가 고칠 것을 1~2개 고르고, 고치는 일은 구현 대화에서 한다.

## 하지 말 것
- 코드 읽기, 코드 고치기
- 눌러 보지 않은 시나리오를 통과로 쓰기
- 새 기능 제안
