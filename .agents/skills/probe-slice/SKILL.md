# 요구사항과 조각

## 언제
인터뷰가 끝나 INTERVIEW.md의 '들은 것·팀장 정정·합의·미룸'이 채워지고, DATA.md '사용 계획'이 확정된 뒤 한 번. REQUIREMENTS.md를 고친 뒤 다시 부르면, 파일은 덮어쓰지 않고 대조표와 두 검사만 다시 한다.

## 읽을 것
- INTERVIEW.md. 단, '## 물을 것' 칸은 사람이 쓰는 질문 메모이므로 읽지도 옮기지도 않는다.
- DATA.md (사용 계획, 확인 숫자, '데이터로 알 수 없는 것')
- `assets/REQUIREMENTS-template.md`

## 순서
1. REQUIREMENTS.md를 틀대로 만든다 (파일이 없을 때만).
   - 핵심 흐름은 "→"로 이은 한 줄. 화살표 하나가 조각 하나이고, 4~5개. 계산하는 과제면 기존 방식 지표를 계산 엔진보다 앞에 둔다.
   - R마다 성공 기준은 정상 하나와 예외 하나. 각각 **보인다 / 막힌다 / 남는다 / 바뀐다** 중 하나로 끝낸다. 계산 기능이면 "기존보다 지표가 나아졌다"는 숫자 비교로 쓴다.
   - 팀장이 1순위·반드시·우선이라고 한 것은 R과 성공 기준에 넣는다.
   - 한계선에는 팀장이 말한 숫자만 쓴다. 팀장에게 듣지 않은 값은 '가정'에 쓴다.
   - 안 만드는 것과 미룸(팀장이 합의한 것만)을 적는다.
2. 대조표(누락 검사)를 만든다. INTERVIEW.md '들은 것·팀장 정정·합의·미룸'의 줄마다, 한 줄에 사실이 여럿이면 나눠서, REQUIREMENTS.md의 어디(R 번호와 성공 기준, 한계선, 가정, 안 만드는 것, 미룸)에 들어갔는지 적는다. 표시는 넷이다.
   - **빠짐**: 어디에도 없다.
   - **격하**: 팀장이 1순위·반드시·우선이라고 한 것이 가정·미룸·안 만드는 것으로만 갔다. 또는 팀장이 말한 숫자가 '가정'에 들어갔다.
   - **추가**: REQUIREMENTS.md에 있는데 INTERVIEW.md와 DATA.md에 근거가 없다(지어낸 조건).
   - **미답**: DATA.md '데이터로 알 수 없는 것' 중 INTERVIEW.md에 답이 없다.
   표: INTERVIEW 줄(팀장 말 그대로, 짧게) | 들어간 곳 | 표시
3. 의존 관계 검사 표: 조각 | 쓰는 결과 | 그 결과를 만드는 조각 | 순서 문제. 결과를 쓰는 조각이 만드는 조각보다 앞에 있으면 '순서 문제'로 표시하고 고친 순서를 제안한다. 지표가 엔진보다 뒤에 있으면 같이 표시한다.
4. 시간 예산 표: 조각 | 바뀌는 파일 1~2개 | 예상 분(조각당 20분 기준) | 확인 방법. 합이 구현 시간을 넘으면 넘는 조각을 '미룸 후보 (팀장 합의 필요)'로 표시한다.

## 멈추는 곳
REQUIREMENTS.md를 저장하고, 대화에 아래 셋만 보여 준 뒤 멈춘다. 코드는 쓰지 않는다.
- 대조표 전체. 빠짐·격하·추가·미답 줄을 맨 위에 두고, 마지막 줄에 "빠짐 n · 격하 n · 추가 n · 미답 n / 전체 n줄"
- 의존 관계 표
- 시간 예산 표

빠짐과 격하를 R로 올릴지, 팀장과 합의해 미룸으로 옮길지는 사람이 정한다. 사람이 고칠 내용을 주면 REQUIREMENTS.md를 고치고, 대조를 다시 해서 빠짐·격하 개수를 한 줄로 보고한다. 조각 순서와 미룸 확정도 사람이 한다.

## 하지 말 것
- 팀장이 말하지 않은 숫자·조건을 사실처럼 쓰기
- 빠짐을 스스로 '가정'이나 '미룸'에 넣어 숨기기, 대조표에서 줄을 생략하기
- 사람이 합의하기 전에 미룸을 확정하기
- '물을 것' 칸의 줄을 요구사항으로 옮기기
